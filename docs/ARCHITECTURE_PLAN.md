# Cielo compiler architecture

This is the final shape of the database port. The design keeps semantic
transitions explicit, keeps algorithms in the crate that owns them, and makes
memory experiments replaceable without teaching the frontend about them.

## The compile graph

```text
SourceFile
  -> ParsedFile
  -> CoreFile
  -> TypedFile
  -> MonomorphizedFile
  -> ClassifiedFile
  -> StagedFile
  -> LinearFile
  -> RuntimeFile
  -> MemoryFile
  -> EmittedFile
```

Each product has one meaning. A later phase does not reach into an earlier
phase's tables.

| Query | Input and result |
| --- | --- |
| `parsed_file` | source text -> AST, diagnostics, interner |
| `core_file` | parsed AST -> lowered Core |
| `typed_file` | Core -> types, effects, and ownership facts |
| `monomorphized_file` | typed Core -> concrete instances |
| `classified_file` | instances -> comptime/runtime classifications |
| `staged_file` | classifications -> residual Core |
| `linear_file` | residual Core -> normalized Linear IR |
| `runtime_file` | Linear IR -> a self-contained `RuntimeProgram` |
| `memory_file` | `RuntimeProgram` + `MemoryProfile` -> memory-lowered CFG |
| `emitted_file` | memory-lowered CFG -> C source |

`cielo-db` keeps these queries in vertical modules:

```text
cielo-db/src/database.rs       Salsa storage and profiling
cielo-db/src/inputs.rs         SourceFile and compile profiles
cielo-db/src/artifacts.rs      phase product types
cielo-db/src/queries/frontend.rs
cielo-db/src/queries/staging.rs
cielo-db/src/queries/runtime.rs
cielo-db/src/queries/memory.rs
```

The driver requests products through the compiler facade. There is no second
production pipeline and no branch based on interner state.

## Salsa policy

`SourceFile` is a Salsa input. A tracked function is a cached, dependency-aware
function. Salsa records the queries called while it runs, so changing source
text invalidates parsing and its dependents, while changing only memory
options leaves parsing, typing, staging, and runtime construction cached.

The query boundary is deliberately coarse:

- source files for parsing;
- files/modules for semantic and staging products;
- files for the current runtime and memory products;
- later, stable function/SCC/instance ids can be introduced without changing
  the product contracts.

Expressions, statements, mutable builders, worklists, liveness sets, and
pass-local caches are ordinary Rust values. There are no per-expression Salsa
queries, tracked IR nodes, Salsa interners, accumulators, persistence,
snapshots, or cycle recovery.

Query wrappers call ordinary Rust passes and do not pass `&dyn Db` into those
passes. Queries return immutable `Arc` products. File writes, C compiler
invocation, linking, and running programs remain driver operations.

`CieloDatabase` records Salsa execution events and exposes query memory
statistics. This makes cache reuse and memo growth measurable without making
profiling part of compiler semantics.

## Phase products

The repeated source/interner fields are generated by a private macro in
`cielo-db/src/artifacts.rs`:

```rust
file_artifact!(TypedFile { typed: TypedCore });
file_artifact!(StagedFile { staged: StagedCore });
file_artifact!(RuntimeFile { runtime: RuntimeProgram });
```

The macro creates separate nominal Rust types. It is not an enum: an enum
would require matching at every boundary and would let a consumer receive an
invalid phase variant. The distinct types make phase mistakes compile errors.

`StagedCore` separates its lasting data from its inspection data:

```text
StagedCore
  program       residual Core used by runtime lowering
  sema          semantic facts still needed by linearization
  facts         constants and residual effect summaries
  report        monomorphization, CT, BTA, and pass counters
```

Runtime lowering reads `program`, `sema`, and `facts`. The driver may read the
report to explain staging decisions. A runtime or memory pass cannot receive a
loose bundle of monomorphization, evaluator, and BTA tables.

`RuntimeProgram` is the semantic firewall. It contains:

```text
CfgProgram
RuntimeValueFacts       CFG-value ownership classes
RuntimeSourceMap        CFG site -> source span
ConstantTable
DiagnosticBag
```

The runtime crate builds this product from Linear IR and semantic facts. The
memory crate receives only this product. It does not receive Core,
`SemanticTables`, `StagedCore`, or staging configuration.

## Crate ownership

Production dependencies point down this DAG:

```text
cielo-base
  <- cielo-frontend
  <- cielo-ir

cielo-base + cielo-frontend + cielo-ir
  <- cielo-lowering

cielo-base + cielo-ir <- cielo-sema <- cielo-staging
cielo-base + cielo-ir + cielo-sema <- cielo-runtime
cielo-base + cielo-ir <- cielo-memory
cielo-base + cielo-ir <- cielo-backend-c

all algorithm crates
  <- cielo-db
  <- cielo-compiler
  <- cielo-driver
```

Important ownership rules:

- `cielo-base` owns ids, spans, symbols, diagnostics, and small containers.
- `cielo-ir` owns Core, Linear, CFG, target data, ownership vocabulary, and
  the runtime contract.
- `cielo-frontend`, `cielo-lowering`, `cielo-sema`, `cielo-staging`,
  `cielo-runtime`, `cielo-memory`, and `cielo-backend-c` own their algorithms.
- `cielo-db` is the only Salsa consumer and only composition layer.
- `cielo-compiler` owns the public facade, compiler configuration, and a
  `CieloDatabase`; it does not own passes.
- `cielo-driver` owns CLI inspection, file I/O, external tools, and execution.
- `cielo-memory` production dependencies are only base and IR.
- `cielo-backend-c` production dependencies are only base and IR.

`cielo-test-support::PassHarness` is a dev-only way for component tests and
benchmarks to call ordinary passes directly. It has no Salsa database and is
not used by the compiler facade or driver. Every test lives under the owning
crate's `tests/` directory; no test modules live under crate `src/`.

## Memory strategies

Only unmanaged passthrough and reference counting are implemented, so those
are the only variants in `MemoryStrategy`. ARC options live inside the
reference-counting variant:

```rust
enum MemoryStrategy {
    Unmanaged,
    ReferenceCounting(ArcConfig),
}

match profile.strategy {
    MemoryStrategy::Unmanaged => unmanaged::lower(input),
    MemoryStrategy::ReferenceCounting(config) => refcount::lower(input, config),
}
```

The database mirrors this dispatch with `unmanaged_memory_file` and
`refcount_memory_file`. Salsa executes only the selected branch. Switching the
profile reuses `runtime_file`; it does not rerun parsing, typing, staging, or
runtime lowering.

The public facade can request several memory profiles from the same database:

```rust
let source = compiler.source(text, source_id);
let arc = compiler.memory(source);
let unmanaged = compiler.memory_with_profile(
    source,
    MemoryProfile::from_preset(MemoryPreset::Unmanaged),
);
```

The driver exposes the implemented profiles directly:

```sh
cargo run -p cielo-driver -- program.cielo --memory unmanaged --dump memory
cargo run -p cielo-driver -- program.cielo --memory arc-optimized --run-c
```

ARC owns its managed-value propagation, CFG liveness, borrow-hazard analysis,
retain/release insertion, optimization, and verification under
`cielo-memory::refcount`. Its analyses consume CFG values and runtime source
spans, not semantic tables.

The output is strategy-shaped as well:

```rust
enum MemoryProgram {
    Unmanaged(UnmanagedProgram),
    ReferenceCounting(ReferenceCountingProgram),
}
```

`ReferenceCountingProgram` owns its ARC report, verifier result, borrow-hazard
report, and trace setting. `UnmanagedProgram` has none of those fields. Common
consumers use `MemoryProgram::cfg()` and `emit_trace_comments()`, so adding a
real collector does not grow a struct full of unrelated optional ARC fields.

When a second real strategy is implemented, add a sibling module with its own
input facts, analyses, report, and query branch. Do not add a placeholder
variant today and do not force unrelated strategies into an ARC-shaped plan.
Only the selected branch should be requested, so unselected analyses do not
run.

The backend receives explicit CFG operations, constants, and an emission
option. It does not know which high-level memory analysis produced them.

## Avoiding cycles

Use these rules when adding a vertical concern:

1. Put shared vocabulary below both algorithms. For example, ownership classes
   and runtime facts live in IR, not in memory or staging.
2. Put interaction above independent algorithms. The database query or a small
   integration module composes effects, staging, concurrency, and memory.
3. If two analyses are genuinely simultaneous, make one solver return one
   product instead of two queries calling each other.
4. Compute recursive SCCs inside one query. Do not rely on an accidental
   Salsa cycle for ordinary compiler recursion.

Modules in a crate may share private helpers. A new crate is justified by a
stable input/output contract, not by a desire to make the dependency graph
look perfectly granular.

## Adding a pass or IR

- A mandatory pass in an existing representation is an ordinary function
  called by that representation's query module.
- A costly reusable result may become a query at file, function, instance, or
  SCC granularity.
- A semantic transition gets a new product type and query.
- Do not add `type_of_expr`, `lower_statement`, or other node-sized queries.
- Passes receive explicit products and relevant profile values, not a universal
  compiler config and not a database service locator.
- Side effects stay outside Salsa.

## Checks

```sh
cargo fmt --all -- --check
cargo check --workspace
cargo test --workspace --no-fail-fast
cargo run -p cielo-driver -- \
  crates/cielo-compiler/examples/v1_test.cielo --run-c
```

The database tests cover cache reuse, source invalidation, strategy-specific
memory dispatch, reuse of runtime products, and query memory statistics.
Runtime and memory tests exercise the firewall directly.

There are no compatibility namespaces, unused boundary summaries, empty
scaffolding directories, or alternate production compiler paths remaining.
